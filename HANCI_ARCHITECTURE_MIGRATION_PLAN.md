# HANCI — Architecture & Lovable-Cloud Exit Plan

Planning document only. No code, database, connection, or configuration was changed.

---

## 1. CURRENT ARCHITECTURE

```text
Browser (React 18 + Vite 5 + TS, react-router v6, 19 routes)
  │
  ├─ src/integrations/supabase/client.ts   (generated; anon key from VITE_* env)
  │     └─ PostgREST  → 19 public tables, RLS on all
  │     └─ GoTrue     → email/password only
  │     └─ Storage    → NOT USED (no buckets exist)
  │     └─ Realtime   → NOT USED (no .channel() / .on() subscriptions)
  │
  ├─ raw fetch: ${VITE_SUPABASE_URL}/functions/v1/chat   (useChat.ts, manual SSE)
  └─ supabase.functions.invoke(...)  → 7 other edge functions
        │
        ▼
Lovable Cloud (managed Supabase project xtdedytqjulxctgkhpbe)
  Deno edge functions: chat, process-media, transcribe-audio, generate-image,
                       ai-smart-features, text-to-speech, yarngpt-tts, translate-voice
        │
        ├─ Lovable AI Gateway  https://ai.gateway.lovable.dev/v1/chat/completions
        │     Bearer LOVABLE_API_KEY  (auto-provisioned, workspace-metered)
        │     → google/gemini-3-flash-preview | 2.5-pro | 2.5-flash | 2.5-flash-lite
        │     → openai/gpt-5, gpt-5-mini, gpt-5-nano, gpt-5.2
        │     → google/gemini-2.5-flash-image
        │
        └─ Direct third-party calls (bypass the gateway):
              Replicate  api.replicate.com/v1/predictions   REPLICATE_API_KEY
              Firecrawl  api.firecrawl.dev/v1/search, /v2/scrape  FIRECRAWL_API_KEY
              Giphy      GIPHY_API_KEY
              YarnGPT    YARNGPT_API_KEY
              ElevenLabs ELEVENLABS_API_KEY
              OpenAI     OPENAI_API_KEY (secret present; no confirmed live call path)
```

Two independent exits are therefore required: **backend exit** (Lovable Cloud → managed Supabase) and **AI exit** (Lovable AI Gateway → Hanci model router). They are separable and should not be attempted together.

## 2. LOVABLE CLOUD DEPENDENCIES

### 2.1 `.env` / build-time environment

**FILE:** `.env`, `src/vite-env.d.ts`
**DEPENDENCY:** `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, `VITE_SUPABASE_PROJECT_ID`, plus non-prefixed `SUPABASE_URL` / `SUPABASE_PUBLISHABLE_KEY`. This file is Lovable-generated and rewritten by the platform.
**CURRENT PURPOSE:** Points the browser client at the Lovable-managed project.
**MIGRATION REQUIRED:** Replace with the new project's URL + anon key, sourced from a `.env` the platform no longer owns (or a build-time secret in the new host). The duplicate non-prefixed keys should be dropped.
**RISK:** HIGH — while the project still lives in Lovable, edits here are overwritten. Env swap must be the *last* backend step, or done after the repo leaves Lovable.

### 2.2 Generated Supabase client

**FILE:** `src/integrations/supabase/client.ts`
**DEPENDENCY:** Auto-generated, marked do-not-edit; hardcodes `localStorage` auth storage.
**CURRENT PURPOSE:** Single browser client used by ~30 call sites.
**MIGRATION REQUIRED:** Becomes a hand-owned file after the exit. Signature stays identical, so no call site changes.
**RISK:** LOW after exit, HIGH before (regeneration reverts edits).

### 2.3 Generated database types

**FILE:** `src/integrations/supabase/types.ts`
**DEPENDENCY:** Regenerated by Lovable after each approved migration.
**CURRENT PURPOSE:** Type safety for every `.from()` call.
**MIGRATION REQUIRED:** Switch to `supabase gen types typescript --project-id <new>` in a script; commit the output.
**RISK:** MEDIUM — a stale types file produces silent `any` drift and compile errors across most pages.

### 2.4 `LOVABLE_API_KEY` in edge functions

**FILE:** `supabase/functions/chat/index.ts`, `process-media`, `transcribe-audio`, `generate-image`, `ai-smart-features`, `text-to-speech`, `translate-voice`
**DEPENDENCY:** `Deno.env.get("LOVABLE_API_KEY")` + hardcoded `https://ai.gateway.lovable.dev/v1/chat/completions`, with Lovable-specific model ids (`google/gemini-3-flash-preview`, `openai/gpt-5.2`, `google/gemini-2.5-flash-image`).
**CURRENT PURPOSE:** All first-party AI: chat, transcription, OCR, summarization, tagging, image fallback.
**MIGRATION REQUIRED:** Route every call through the Hanci model router (section 4). The key itself does not migrate — it is workspace-scoped and stops being provisioned once outside Lovable.
**RISK:** HIGHEST — this is the app's core loop. Nine call sites, three different response shapes (SSE stream, JSON completion, multimodal image response).

### 2.5 Lovable-managed secrets store

**FILE:** platform-managed (surfaced as `Deno.env` in functions)
**DEPENDENCY:** `LOVABLE_API_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_DB_URL` are injected automatically; `FIRECRAWL_API_KEY` is connector-managed and only editable through Lovable Connectors.
**CURRENT PURPOSE:** Server-side credentials.
**MIGRATION REQUIRED:** On managed Supabase the four `SUPABASE_*` values are still auto-injected — no action. `FIRECRAWL_API_KEY` must be re-obtained directly from Firecrawl because the connector-managed value is not exportable. `LOVABLE_API_KEY` is replaced by per-provider keys.
**RISK:** MEDIUM — Firecrawl silently degrades (web search returns nothing, link transcription throws) rather than failing loudly if the key is absent.

### 2.6 `supabase/config.toml`

**FILE:** `supabase/config.toml`
**DEPENDENCY:** Lovable-generated, pins `project_id` and sets `verify_jwt = false` on six functions.
**CURRENT PURPOSE:** Function deploy config.
**MIGRATION REQUIRED:** Rewrite `project_id`; flip `verify_jwt` per section 12; add `[api]`/`[auth]` blocks that Lovable currently manages implicitly.
**RISK:** MEDIUM — mis-set `verify_jwt` either breaks every AI call or leaves the endpoints open.

### 2.7 Automatic edge-function deployment

**FILE:** all of `supabase/functions/*`
**DEPENDENCY:** Lovable deploys on write; there is no CI, no `supabase functions deploy` step, no tests.
**CURRENT PURPOSE:** Zero-friction deploys.
**MIGRATION REQUIRED:** Add an explicit deploy path (Supabase CLI in GitHub Actions, or manual `supabase functions deploy <name>`), plus a `supabase link`ed local repo.
**RISK:** MEDIUM — the first post-exit change silently does nothing until a deploy pipeline exists.

### 2.8 Lovable-specific authentication behaviour

**FILE:** `src/integrations/supabase/previewAuthStorage.ts` (platform file), `src/pages/Auth.tsx`
**DEPENDENCY:** The Lovable preview injects a session into localStorage for in-editor testing. Auth itself is plain GoTrue — no Lovable-specific auth API is used.
**CURRENT PURPOSE:** Preview convenience only.
**MIGRATION REQUIRED:** Delete the preview storage shim after exit; nothing else.
**RISK:** LOW.

### 2.9 Lovable-specific storage

**DEPENDENCY:** None. There are zero buckets and zero `storage.from()` calls.
**MIGRATION REQUIRED:** Nothing to migrate — storage is greenfield, which is fortunate.
**RISK:** NONE for migration; HIGH as a product gap.

### 2.10 Non-Lovable but co-migrating dependencies

Replicate, Giphy, YarnGPT, ElevenLabs, OpenAI keys are ordinary secrets the user owns. They are re-entered into the new project's secret store verbatim. **RISK: LOW.**

## 4. AI PROVIDER MIGRATION — the Hanci model router

### 4.1 Target flow

```text
caller (edge fn / skill / agent)
  → ModelRequest {capability, messages|input, modelHint?, projectId, userId,
                  stream?, schema?, tools?, budget?}
  → Router
      · resolve model: explicit hint → skill preference → user setting → capability default
      · quota check (user + provider), see §13
      · select adapter
  → Adapter (per provider: openai | anthropic | google | replicate | elevenlabs | local)
      · translate ModelRequest → provider-native body
      · call provider
      · translate provider response → NormalizedResponse
  → NormalizedResponse {text?, parts[], toolCalls[], structured?, media[],
                        usage{inputTokens,outputTokens,cost}, model, provider,
                        finishReason, raw?}
  → caller (SSE re-encode for streaming)
```

Adapters are the only place provider SDKs or wire formats may appear. The router never branches on provider name; it branches on **declared capability**.

### 4.2 Capability registry

Each `(provider, model)` entry declares what it can do, so the router can refuse or downgrade rather than fail at request time:

```
capabilities: text_in, image_in, audio_in, video_in, document_in,
              text_out, image_out, audio_out,
              streaming, tool_calls, parallel_tool_calls,
              structured_output {none|json_mode|strict_schema},
              reasoning, context_window, max_output_tokens,
              cost_per_1k_in, cost_per_1k_out, free_tier?
```

### 4.3 Documented provider differences (as known today; verify against live docs before implementing)

| Concern | OpenAI | Anthropic | Google Gemini | Replicate | ElevenLabs / YarnGPT |
|---|---|---|---|---|---|
| Endpoint style | Responses API for newer models; chat/completions for older | Messages API (`/v1/messages`), own SSE event names | Native `generateContent` **and** an OpenAI-compatible shim | Async predict + poll | REST, binary audio out |
| Streaming | Yes | Yes, different event taxonomy | Yes | No — poll for completion | Yes (chunked audio) |
| Structured output | Strict `json_schema` (schema must be all-required, no format/bounds) | Tool-call-as-schema idiom; no native strict mode | `responseSchema` / `responseMimeType`; not identical to OpenAI strict | N/A | N/A |
| Tool calls | `tools` + `tool_choice`, parallel calls | `tools` with `input_schema`, `tool_use`/`tool_result` blocks | `functionDeclarations`, differing arg encoding | N/A | N/A |
| Image input | URL or base64 | base64 blocks; **no URL fetch** | URL or inline base64 | N/A | N/A |
| Audio input | Whisper/dedicated STT endpoints | **No native audio input** | Native multimodal audio (this is what Hanci uses today) | Whisper models available | STT not applicable |
| Video input | Not supported | Not supported | Native video understanding (limited duration) | Model-dependent | N/A |
| Documents | PDF inline | PDF inline | PDF inline; non-PDF must be pre-extracted | N/A | N/A |
| Image generation | Images API, multipart edits | **None** | Image-capable Gemini models | Wide model catalogue (SDXL etc.) | N/A |
| Token param name | `max_completion_tokens` on newer models | `max_tokens` (required) | `maxOutputTokens` | model-specific | N/A |
| Temperature | Rejected on some newer models | Accepted | Accepted | model-specific | N/A |
| Free tier | No | No | Yes, rate-limited | No (credit) | Limited |

**Consequences for Hanci:** Anthropic cannot serve the audio/video transcription paths — those must stay on Gemini (or move to a dedicated STT provider). Anthropic cannot serve image generation — that stays Replicate/Gemini. So the router must support *per-capability* provider routing, not a single global "provider" setting.

### 4.4 Migration mechanics

1. Introduce `supabase/functions/_shared/model-router.ts` with a single Lovable adapter that reproduces today's behaviour byte-for-byte.
2. Convert call sites to the router one at a time, starting with the low-risk ones (`ai-smart-features`), ending with `chat`.
3. Add OpenAI/Anthropic/Google adapters behind the same interface.
4. Only then remove the Lovable adapter.

This sequencing means the AI exit never requires a big-bang cutover, and it can happen either before or after the Supabase exit.

## 6. FILE / KNOWLEDGE ARCHITECTURE

```text
client picks file
  → validate (type, size, per-user storage quota)
  → upload to Storage bucket `documents`  path: {user_id}/{project_id|_}/{doc_id}/{filename}
  → insert documents row (status=uploaded)
  → invoke ingest-document (async, service-role)
       ├─ extract   → text + page/timestamp map      (status=extracting)
       ├─ chunk     → ~800 tokens, ~15% overlap,     (status=chunking)
       │              respecting page/heading/segment boundaries
       ├─ embed     → batch → document_chunks.embedding (status=embedded)
       └─ enrich    → optional: entity + event extraction → knowledge_items/events
  → client polls or subscribes to the documents row status
```

**Buckets (all private, RLS on `storage.objects` scoped to `owner`/path prefix):**
- `documents` — original uploads, retained permanently and always re-downloadable via signed URL.
- `generated` — generated images/audio.
- `avatars` — public-read is acceptable here only.

**Per-type extraction:**

| Type | Extraction | Preserved locators |
|---|---|---|
| PDF | text layer; OCR fallback via a vision model for scanned pages | page number |
| DOCX | client- or server-side docx parser → text (vision models will not accept raw docx) | paragraph index |
| TXT / Markdown | direct; keep heading hierarchy | heading path |
| Images | vision model caption + OCR | region (optional) |
| Audio / Video | STT (Gemini multimodal today) → timed segments; store duration + segment timestamps | timestamp span |

**Every chunk and knowledge item carries provenance:** `source_document_id`, `source_locator` (page/timestamp/heading), `source_date` (document date, distinct from `captured_at`), `project_id`, `entity_ids[]`, `confidence` (0–1, extraction certainty), `status` (`current｜superseded｜rejected`). Nothing enters retrieval without provenance — that rule is what makes the workspace trustworthy.

**Retrieval:** one RPC, `search_knowledge(query_embedding, query_text, project_id, limit, filters)`, doing hybrid vector + tsvector with reciprocal-rank fusion and project scoping. Chat grounding, global search, and skills all call this one function. This replaces both the current keyword-only `match_nigerian_knowledge` and the in-memory title filter in `QuickSearchModal`.

## 7. PROJECT MODEL

```text
project
 ├─ conversations   (conversations.project_id, NULLABLE)
 ├─ documents       (documents.project_id)
 ├─ entities        (people, companies — project-scoped or global)
 ├─ events          (decisions, meetings, milestones)
 ├─ tasks           (a lightweight table, or events with kind='task' initially)
 ├─ knowledge_items (durable memory scoped to the project)
 └─ settings        (system_prompt, default_model, retrieval on/off)
```

**Context scoping rule — three levels, chosen per conversation:**

1. `none` — no retrieval, no memory. A scratch chat.
2. `project` (default when `project_id` is set) — retrieval limited to that project's documents, knowledge, entities, and events; the project's system prompt applies.
3. `global` — explicit opt-in; searches across all projects.

Because `conversations.project_id` is nullable and the scope is a per-conversation column rather than a global user setting, attaching a chat to a project never forces every other chat to inherit that context. Moving a conversation into a project is a single `UPDATE` and re-scopes retrieval from the next message onward — prior messages keep their recorded provenance.

## 8. MEMORY MODEL

Two tables, deliberately not one.

### DURABLE MEMORY — `knowledge_items`

Stable facts and preferences: "prefers concise answers", "works in Lagos", "the stack is React + Supabase".

```
id, user_id, project_id (nullable = global), key, value, category,
confidence, status (current|superseded|rejected),
supersedes_id, source_type (chat|document|manual|extraction),
source_ref (message_id | document_id + locator),
valid_from, captured_at, updated_at
```

Writes are upserts on `(user_id, project_id, key)`; the previous row is set `status='superseded'` with `supersedes_id` pointing forward, never deleted. Retrieval reads `status='current'` only.

### EVENT MEMORY — `events`

Things that happened at a point in time: decisions, meetings, milestones.

```
id, user_id, project_id, kind, title, body,
event_date        -- when it happened
captured_at       -- when Hanci learned it
status (current|superseded), supersedes_id,
confidence, source_type, source_ref, entity_ids[]
```

**Distinguishing an old decision from the current one** relies on three fields together: `event_date` orders reality, `captured_at` orders knowledge (a decision learned late is still an old decision), and `supersedes_id` records the explicit chain. The current decision on a topic is the `status='current'` row with the latest `event_date`; the chain via `supersedes_id` gives the full history on request. Conflicting extractions land as separate rows with their own confidence rather than overwriting — the assistant surfaces the conflict instead of silently picking one.

Migration: today's `user_memory` splits — the true facts become `knowledge_items`, and the settings-shaped keys (`custom_instructions`, `tone`, `nickname`, `occupation`, `about_you`, `ref_*`) move to `user_settings`.

## 9. SKILLS

A skill is a stored, versioned, executable workflow definition.

```
skills
  id, user_id, project_id (nullable = available everywhere),
  name, purpose, instructions (system prompt / plan template),
  input_schema  jsonb (JSON Schema),
  output_schema jsonb (JSON Schema, drives structured output),
  allowed_tools text[]        -- connector tool ids; empty = no tool access
  preferred_models jsonb      -- {primary, fallback[]} per capability
  requires_approval bool      -- pause before any write-scope tool call
  max_steps int, max_cost_credits numeric,
  enabled bool, version int, created_at, updated_at

skill_runs
  id, skill_id, user_id, project_id, conversation_id (nullable),
  input jsonb, output jsonb, status (queued|running|awaiting_approval|succeeded|failed|cancelled),
  error, model_used, tokens_in, tokens_out, cost,
  started_at, finished_at
  → tool_calls (shared table, run_type='skill')
```

**Execution engine (the only part to build):**
`validate input against input_schema` → `resolve model via router` → `assemble context (project scope + retrieval)` → `loop: model call → tool call → observation` (bounded by `max_steps`, pausing at `requires_approval` for write tools) → `validate output against output_schema` → `persist skill_run + tool_calls + usage_events`.

The five named skills (WhatsApp Analyst, Daily Review, YouTube Script, Scholarship Assistant, Job Application) are then **data rows**, not code. That is the test of whether the engine is right: adding a skill must require no deployment.

```
  id, connector_id, name, description,
  input_schema jsonb, side_effect (read|write),
  requires_approval bool, enabled bool
```

**Per provider, as known — exact OAuth endpoints, scope strings, and flows must be read from each provider's current documentation at implementation time; none are invented here:**

- **Notion** — OAuth-based integration authorization; access is granted per selected page/database, so the connection must record *which* resources were shared, not just "connected". Tools: search, read page/database, query database, append/create (write).
- **GitHub** — supports both a personal access token and a GitHub App / OAuth app flow; the App path is the one that gives per-repository scoping. Tools: list repos, read file, search code, list/create issues (write), create PR (write).
- **Firecrawl** — plain API key, no OAuth. Tools: search, scrape, crawl. Already used server-side today, so this is a formalization rather than a new integration.
- **MCP servers** — not a fixed provider: a connection is a server endpoint plus a transport and an auth mode, and the tool list is **discovered at runtime** from the server rather than stored statically. `connector_tools` rows are therefore a cache with a refresh timestamp for MCP connections.

**Invariants:** tokens live only in Vault/encrypted storage referenced by `credential_ref`; every tool declares `side_effect`; every write-scope tool defaults to `requires_approval = true`; the skill/agent runtime may only call tools present in the caller's `allowed_tools` ∩ the user's enabled connector tools; every invocation writes a `tool_calls` row and an `audit_events` row.

## 11. AGENTS (design only)

```
agent_runs
  id, user_id, project_id, agent_key, task text,
  plan jsonb,                    -- ordered steps, revisable mid-run
  state jsonb,                   -- scratchpad carried between steps
  status (planning|running|awaiting_approval|paused|succeeded|failed|cancelled),
  step_count, max_steps, retry_count, max_retries,
  cost, tokens_in, tokens_out,
  result jsonb, error,
  created_at, started_at, finished_at

agent_steps
  id, run_id, ordinal, kind (plan|model_call|tool_call|approval|observation|reflection),
  input jsonb, output jsonb, model, tokens, duration_ms, status, error

tool_calls (shared with skills, run_type='agent')
audit_events (every approval, every write-scope tool call)
```

**Behaviour:** plan → act → observe → revise, bounded by `max_steps`, `max_retries`, and a cost ceiling. Retries are per-step with exponential backoff and only for retryable failures (429/5xx per the gateway error contract) — a terminal error fails the step. Any write-scope tool, or any step a skill marked `requires_approval`, transitions the run to `awaiting_approval` and persists state so it can resume later — runs must be durable across function invocations, which means the loop is driven by a queue/scheduler, not by one long-lived HTTP request. Every step is auditable; the run is fully reconstructable from `agent_steps` alone.

Agents are last for a reason: they are only as good as retrieval, skills, connectors, and quotas beneath them.

## 12. SECURITY

### Functions that MUST become `verify_jwt = true`

| Function | Today | Required | Why |
|---|---|---|---|
| `chat` | `false` | **`true`** | Highest cost per call; currently callable by anyone holding the public anon key. |
| `transcribe-audio` | `false` | **`true`** | Accepts arbitrary uploads; multimodal cost. |
| `text-to-speech` | `false` | **`true`** | Metered ElevenLabs cost. |
| `yarngpt-tts` | `false` | **`true`** | External metered cost. |
| `translate-voice` | `false` | **`true`** | Model cost. |
| `generate-image` | `false` | **`true`** | Replicate credits — the most directly expensive endpoint. |
| `process-media` | not configured (default) | **`true`** | Large uploads + model cost. |
| `ai-smart-features` | not configured (default) | **`true`** | Model cost. |

There is no legitimate anonymous caller for any of the eight. The only exception to design around later is a public shared-conversation read path, which should be a separate, narrowly-scoped function — not an exemption on `chat`.

### Additional requirements

- **Server-side identity:** every AI function must derive `user_id` from the verified JWT (`auth.getUser()` on the request's Authorization header), never from the request body. `useChat` currently sends only the anon key; it must send the session access token.
- **Per-user quotas** enforced *before* the provider call, reading `quotas` and writing `usage_events` after (section 13).
- **RLS everywhere**, with new tables using `TO authenticated` and `auth.uid()` scoping from the first migration; `service_role` grants only where edge functions genuinely need them.
- **Private storage only.** Signed URLs with short expiry; `storage.objects` policies keyed on the `{user_id}/...` path prefix. Never a public bucket for user documents.
- **Secrets** stay in the Supabase secret store / Vault. No `VITE_`-prefixed provider key, ever.
- **Connector tokens** in Vault via `credential_ref`; revocation must be one row update that immediately disables the tools.
- **Tool permission scopes:** read vs write separation, approval gates on writes, and an `audit_events` row per privileged action.
- **Input limits:** max upload size, max messages per request, max context tokens — enforced server-side, since the client limits are advisory.

## 13. FREE-TIER / COST CONTROL

- **Quota table** per `(scope, provider, window)` — daily and monthly, per user and global. Checked before dispatch; a breach returns a structured, user-visible error, never a silent generic reply.
- **Usage tracking:** one `usage_events` row per model call with real token counts and computed cost, written even on failure (a severed generation is still billed upstream).
- **Model fallback chains** declared per capability, e.g. `[gemini-flash (free tier) → gpt-5-mini → gpt-5]`, walked on 429/5xx only. Terminal statuses (400/401/402/403) never trigger fallback.
- **Request limits:** per-minute and per-hour caps per user, independent of token cost, to blunt abuse of the now-authenticated endpoints.
- **Token limits:** cap input context (truncate oldest turns, prefer retrieval over raw history) and output tokens per capability; refuse rather than truncate for structured output.
- **User-configurable model selection** in `user_settings`, constrained to models the user's quota allows — and a "cheapest that can do the job" default.
- **Streaming for anything long-running** — a buffered call that emits nothing for ~2 minutes is severed by the host, still billed, and retried by SDK defaults, which can triple the cost of a single request.
- **Honest copy:** local chats, projects, and files may be presented as unlimited (bounded only by storage). External model usage must never be described as unlimited anywhere in the UI.

## 14. MIGRATION ORDER (adjusted to this codebase)

**Phase 0 — Preconditions (no migration yet)**
1. Freeze schema changes in Lovable. Take a full `pg_dump` (schema + data + `auth` schema) and store it safely.
2. Reconcile the duplicate tables on paper: decide the `documents`/`uploaded_documents` merge and the `message_sources` promotion. Both tables are empty, so this is a schema-dump edit rather than a data migration.
3. Introduce `_shared/model-router.ts` with a Lovable-only adapter and move `ai-smart-features` onto it. Zero behaviour change; proves the abstraction.

**Phase 1 — Backend exit**
4. Create the managed Supabase project; enable `vector`.
5. Restore corrected schema → RLS → functions → triggers → new indexes.
6. Restore `auth.users` (preserving UUIDs), then table data in FK order.
7. Re-enter secrets; issue a **new** Firecrawl key.
8. `supabase link`, deploy all eight functions, rewrite `config.toml`.
9. Point a staging build at the new project; verify auth, chat streaming, history load, admin gate, image generation, transcription.
10. Cut production env vars over. Keep the Lovable project read-only as a rollback for two weeks.

**Phase 2 — Lock down**
11. Flip `verify_jwt = true` on all eight functions **and** ship the client change that sends the session token in the same release. Add `usage_events` + `quotas` and enforce them.

**Phase 3 — AI exit**
12. Add OpenAI / Anthropic / Google adapters behind the router; migrate call sites low-risk first, `chat` last.
13. Remove the Lovable adapter and `LOVABLE_API_KEY`.

**Phase 4 — The brain**
14. Storage buckets + merged `documents` + upload pipeline (real persistence).
15. `projects` table + migrate `localStorage` payloads + `project_id` on conversations/documents/images.
16. `document_chunks` + embeddings + the unified `search_knowledge` RPC; retire keyword-only retrieval and the in-memory search modal.
17. `knowledge_items` + `events` + `entities` (memory model), splitting `user_memory`.
18. Skills engine + migrate `hanchi_custom_gpts`.
19. Connectors (Firecrawl first — it already works server-side — then GitHub, Notion, MCP).
20. Agent runtime.

**Two deliberate deviations from the suggested order:** the AI abstraction starts in Phase 0 (a no-op adapter costs nothing and de-risks step 12 enormously), and endpoint lockdown moves *before* the AI exit, because open metered endpoints are a live liability that should not wait behind a multi-provider refactor.

## 16. FINAL RECOMMENDATION

**Can Hanci safely evolve into the target architecture?**
Yes. The chat core, RLS discipline, and edge-function boundary are genuinely reusable. The workspace layer is *absent* rather than wrongly built, which makes it additive work. The real debt is small and well-identified: two localStorage features, two duplicate table pairs, and one overloaded jsonb column.

**Should we keep the existing project?**
Yes. Rebuilding would discard a working streaming chat pipeline, a correct security-definer admin model, a functioning multimodal media pipeline, and a complete design system — and would reintroduce the same bugs. The exit is a migration, not a rewrite.

**Should we migrate before building the brain?**
Yes — but only the *backend* exit. Building projects, storage, retrieval, skills, and connectors on Lovable Cloud means building them twice: every new table is a table to re-migrate, and every generated-file edit is reverted. The *AI* exit can safely wait, provided the router abstraction is introduced first as a no-op.

**Which 3 tasks should happen first?**
1. **Full backup + schema reconciliation on paper** — dump everything including the `auth` schema, and finalize the `documents`/`uploaded_documents` merge and the `message_sources` promotion so the migration carries the corrected schema rather than the current one.
2. **Introduce the model-router abstraction with a Lovable-only adapter** and move `ai-smart-features` onto it — zero user-visible change, and it removes the single largest risk from the eventual provider swap.
3. **Export the localStorage Projects and Custom GPTs to the database** — this is the only data in the system that no server-side migration can rescue, and it is one browser-cache clear from being gone.

**Which existing features should NOT be touched yet?**
- `useChat`'s SSE parser and the `chat` function's streaming path — freeze until the backend migration is verified.
- `messages.metadata` shape — additive changes only.
- `is_admin()` and the admin RLS policies — the only working privilege boundary.
- The `process-media` chunked base64 handling — naive edits reintroduce stack-overflow crashes on large files.
- The design system, routing, and page layouts — no visual work during a backend migration; it makes regressions impossible to attribute.
- Mock features (Apps, Discover, plugin registry) — leave them inert. Deleting them now creates churn; they are replaced wholesale by connectors in Phase 4.
